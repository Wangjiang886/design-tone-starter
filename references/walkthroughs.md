# 两个完整走法示例

下面是说明流程的虚构对话，不是实际生成、外部智能体回复或显卡测试记录。示例名称和素材编号只用于演示。

## 示例 A：摄影作品展示页

**用户**：我想做一个摄影作品页，刚开始，不知道怎么说。

**助手第一轮**：先给这个项目起个名字，告诉我保存位置。我会建立项目分区。你更想展示作品、接拍摄预约，还是讲个人经历？

用户给出目录与“展示作品”后，助手建立分区，再问：“给我一个喜欢的参考链接或图片。最后希望更像安静的画册，还是信息清楚的作品目录？”

**用户**：上传了参考截图，希望像安静的画册，但作品要好找。

**助手分析**：读取实际截图，说明观察到的留白、图文比例、导航与颜色。提出保留大图和留白、增加按系列筛选的建议，问用户是否按这个方向。

用户选择后，将决定写入简报和定调方案。步骤与目标包括：先整理作品系列，再准备封面和说明，交第二视角复核，最后做首页预览。

**资料清单示例**：

| 需要什么 | 用在哪里 | 什么算找对 |
|---|---|---|
| 系列封面照片 | 首页导航 | 主体清楚，横向裁切仍能理解 |
| 系列名与短说明 | 作品目录 | 与照片内容对应，文字来自用户 |
| 个人介绍与联系方式 | 简介页 | 用户确认可以展示的真实信息 |

素材入库后，助手向第二个有图像能力的 agent 提供实际照片和用途。若接口不可用，生成交接单，由用户发给豆包并带回反馈。未带回前进度写 `pending`。

假设用户带回的反馈指出一张照片适合正文、不适合裁成封面，助手将该素材的封面用途标待调整，保留原件，询问替换哪张。

资料选择完成后，制作方先做首页，并交真实网页预览。用户提出“系列筛选要更醒目”，助手只修改对应部分和必要联动，记录版本。

用户确认后登记最终方案与交付入口。此项目无口播需求，声音阶段跳过；不询问配音，也不生成背景音乐。

## 示例 B：30 秒原理讲解的静音视觉原型

**用户**：我想解释风扇为什么会送风，给初中生看，30 秒，有参考视频。

**助手**：读取参考视频或如实说明读取限制。问最终希望偏实物结构演示，还是图形解释；推荐先由 Gemini／豆包写短文案，让用户选择是否文案前置。

用户选择先写文案后，助手整理写稿需求，用户确认解释内容，再把稿件落盘。没有可靠资料的科学表述保留待核对，不因为稿件已写就当成事实已证实。

**阶段计划示例**：

1. 找清楚叶片形状和气流方向：产出有来源的结构资料与参考；完成依据是能够支持文案解释。
2. 找动作参考与标注素材：原件进入素材库，清单标出分别服务哪个画面。
3. 请第二个有视觉能力的 agent 核对叶片、旋转和气流标注是否用对；真实反馈存入过滤库。
4. 先做开头一段静音浏览器原型，验证是否看得清结构和变化；用户选择通过后继续其余段落。
5. 通过网页 URL 预览与返工，提供可暂停和重新播放的入口，不导出 MP4。
6. 用户确认视觉版本后，整理完整画面与口播时间表，交豆包做 TTS 和音效。

如果资料还缺气流方向的依据，助手回清单补资料或询问是否先缩小讲解目标，不让第二个 agent 靠图片气氛猜结论。

如果只有本机 `localhost`，豆包无法直接访问。助手列出需交给用户的实际画面、时间点和文案；不能把本地网址发过去后说豆包看完了。

如果本机硬件加速未检查，预览记录中写 `not_verified`。视觉方向验证与 GPU 使用验证分开，避免为了证明技术而反复生成整片。

此阶段最终交付是静音网页视觉和声音交接单。只有收到实际音频文件时，才登记声音文件完成；没有声音需求则视觉版也可按本次约定交付。

## 续作示例

用户第二天说“接着改昨天的首页”。助手先读进度与反馈，找到 `iterate` 阶段和预览入口；不重新询问项目方向，也不重建素材库。

如果真实入口已经失效，先恢复运行位置或说明缺失文件；保留已确认方案，不把“文件夹还在”当成预览可用。
